判断を変更するときは、可能な限り過去の記録を削除せず、置き換えた判断を追記します。

## D-007 初期のAI変更はbranch / PR経由にする

状態: SUPERSEDED BY D-012

### 判断
リポジトリ初期化を除き、AIによるまとまった変更はbranchで作成し、人間が確認できるPRとして提示する。AIが勝手にmainへmergeしない。

### 理由
外部長期記憶そのものをAIが無監督で確定変更することを避けるため。

### 変更理由
長時間開いたPRへ反復pushすると、Codex等の自動PRレビュー連携を不要に繰り返し起動し得ることが判明した。branchでの作業とPR提示のタイミングを分離するD-012へ置き換えた。

## D-012 work branchとPR作成を分離する

状態: SUPERSEDED BY D-013

### 判断
AIによるまとまった変更はwork branch上でまとめて作業し、作業中は原則PRを開かない。自己確認と必要な状態更新が終わったレビュー境界でPRを1回だけ作成する。

### 理由
Codex等の自動PRレビューがPR作成・Ready化・pushなどをトリガーに起動し得るため、PRをレビュー境界へ限定して不要な自動処理を減らすため。

### 変更理由
このrepoではPRを1回作るだけでもCodex / Cursorの外部GitHub Appが反応することが確認された。内部AI作業ではPR自体を使わないD-013へ置き換える。

## D-013 内部AIレビューはbranch比較で行う

状態: ACTIVE

### 判断
内部AI作業では、通常のレビュー手段としてPull Requestを使わない。

標準手順を次とする。

1. `main` からwork branchを作る
2. branch上で変更を完了する
3. `main...work branch` のcompare結果を人間へ提示する
4. 人間が明示的に承認する
5. `main` を確認済みcommitへfast-forwardする
6. 不要になったwork branchを削除する

Pull Requestは、外部Contribution、GitHub上に公開レビュー履歴を残す必要がある場合、または人間が明示的に要求した場合だけ使う。

### 理由
PR #1で `chatgpt-codex-connector[bot]` と `cursor[bot]` がPRイベントに反応した。GitHub Actions CIではなく外部Appのhookであり、内部レビューをbranch比較へ変更すれば人間確認を維持したままPRイベント自体を避けられるため。

## D-014 小説を主目的とし、研究は制作工程として使う

状態: ACTIVE

### 判断
本プロジェクトの主目的を小説制作とする。

研究・追試・技術史調査は、作品を現実に近づけ、物語上の疑問を検証するために必要な箇所から行う。

基本ループを次とする。

**物語を書く → 技術的な疑問が出る → 原典を読む → 必要なら追試する → 理解を更新する → 小説へ戻す**

制作中に独立した研究価値のある問いが見つかった場合は、物語から枝分かれして追加実験してよい。

### 理由
研究を先に積み上げ続けると、小説が従属しやすい。一方、実際の調査・追試は作品のリアリティと学習価値を高め、予想外の結果が物語を改善する可能性があるため。

## D-015 公開可能な作業記憶を別層で持つ

状態: ACTIVE

### 判断
`notes/working-context.md` を、別セッションへ現在の探索状態を引き継ぐための高速な作業記憶として使用する。

このファイルは正本ではなく、現在の有力仮説、競合説明、未解決点、次の作業を要約して保持する。採用された内容は適切な正本へ昇格させる。

同時に、逐語的なAI内部推論・内部指示・credential・秘密値・公開不能な個人情報は保存対象から除外する。

### 理由
`README / POLICY / canon / findings / decisions` は安定した長期記憶として機能する一方、確定前の探索状態を保持しにくい。会話だけに探索状態が残ると、別セッションで文脈が失われる。

ただし生の思考系列を保存するとノイズ・情報漏洩・秘密情報混入のリスクが増えるため、再開に必要な状態要約だけを外部化する。

## D-016 Pagesは連載小説の読書導線を最優先する

状態: ACTIVE

### 判断
GitHub Pagesの公開サイトは、研究紹介サイトではなく**連載小説を読むサイト**として設計する。

基本構造を次とする。

- トップページの最上位CTAを「小説を読む」にする
- `docs/novel/index.html` を目次とする
- 各話は `docs/novel/001.html`, `002.html`, `003.html` ... の連番で公開する
- 各話ページの上部と下部に `前話 / 目次 / 次話` を置く
- 本文は専用の `docs/novel/reader.css` で長文読書向けにする
- 研究・実験は `docs/research/` へ分離し、読書中の主導線から一段下げる
- 本文正本は `novel/chapters/NNN.md` とし、公開HTMLだけを独立更新しない
- 話数増加で手動同期が負担になった時点でMarkdownからHTMLへの生成を自動化する

### 参考にした公開サイトのパターン

視覚デザイン自体はコピーせず、連載読書の情報設計だけを参考にする。

- カクヨム: 作品概要から「1話目から読む」または目次へ入り、本文末から次エピソードへ進める
- 小説家になろう: 連載作品に目次ページと作品閲覧ページを分け、閲覧ページには表示調整を持たせる
- The Wandering Inn: 独立したTable of Contentsと章ごとのPrevious / Next navigationを持つ

### 理由
D-014の「小説を主目的とする」を公開サイトの情報設計にも反映するため。作品紹介や研究説明が先に来る構成より、読者が最短で第1話へ入り、そのまま次話へ進める構成を優先する。

2026-08-19に `work/novel-reader-site` を人間レビューし、受理されたため `ACTIVE` とした。

## D-017 ペルソナと環境から物語を創発させる

状態: ACTIVE

### 判断
完成済みの未来プロットを先に作って人物へ演じさせる方式ではなく、人物ごとの局所状態と世界（環境）の相互作用から物語を進める。

### 実体の分離

- ペルソナ定義は `novel/personas/` にペルソナごとに独立して持つ
- 世界・環境の定義は `novel/environment.md` に独立して持つ
- 時間に依存するペルソナ状態は `novel/state/personas/` に分離する
- 時間に依存する世界状態は `novel/state/world.md` に分離する
- ペルソナ数は固定せず、物語の進行に応じて `PER-xxx` を追加する

### 時系列上の結合

ペルソナと世界は別々の状態領域だが、**時間方向には独立して更新しない**。

各状態は共通のstory timeと `novel/events/EVT-xxx` によって因果的に接続する。

```text
(P_1(t), P_2(t), ..., W(t))
          |
          | EVT-k
          v
(P_1(t+1), P_2(t+1), ..., W(t+1))
```

同じeventでも各ペルソナが観測する部分は異なるため、世界が変化しても知らない人物は知らないままでよい。変化しなかった状態は前時点から継承し、毎時点に完全snapshotを複製する必要はない。

### 創発生成

- ペルソナは未来の物語、未観測Canon、他者の非公開状態、作者側の長期探索仮説を知らない
- 各ペルソナは、その時点の知識・信念・目的・認知スタイル・関係・記憶・状況から行動する
- 他者の行動や環境結果を実際に観測した範囲で、その人物の状態を更新する
- 行動結果は `novel/environment.md` の規則と `novel/state/world.md` の現在状態から解決する
- ペルソナは「面白い展開」や「予定した結末」を目的にしない
- 本文は、相互作用で成立した出来事を描写する

起承転結は、この過程で成立した状態遷移を整理する再帰構造として使う。各 `起 / 承 / 転 / 結` は内部に再び起承転結を持ち、深さ・章数・scene数を事前固定しない。

「次は転だから事件を起こす」のように構造ラベルを原因として人物を動かさない。実際の相互作用で既存状態が維持不能になる変化が成立した後に `転` と認識する。

story time上の因果順と、小説本文で読者へ提示する章・scene順は分離する。過去場面を後から描写しても、そのペルソナ状態・世界状態は本来のstory timeへ属する。

### 理由
作者・AI・登場人物が同じ未来脚本を共有すると、人物が設定を演じるだけになり、人物同士が事実的に影響し合う余地が小さくなる。

また、ペルソナ定義と現在状態、世界定義と現在状態を混ぜると、人物や世界が時間とともにどう変わったかを復元しにくい。

実体を独立させたまま、状態だけを共通の時系列eventで結合すれば、ペルソナが増え続けても、誰がいつ何を知り、何を信じ、世界がどう変わったかを因果的に追跡できる。

D-014の「小説を主目的とする」と、既存の再帰的起承転結を、実際の制作手順へ接続するための判断でもある。

2026-08-20に `work/persona-environment-fractal-policy` の内容が人間受理され、`main` へfast-forwardされたため `ACTIVE` とする。

## D-018 Bootstrapで物語開始状態を同期する

状態: PROPOSED

### 判断
物語開始時、大きな時代・環境切替、AIセッション変更後の再構成では、背景を寄せ集めて各ペルソナを個別に作り直すのではなく、`novel/bootstrap/BOOT-xxx`を共通の初期化源として使う。

Bootstrapは未来のあらすじではなく、そのtarget story timeまでに成立している背景をまとめた同期Frameとする。

- 世界状態と各ペルソナ状態を同じ`BOOT / story time / parent event head`へ同期する
- 同じ背景を使っても、ペルソナごとに情報projectionを分ける
- Bootstrap本文を全人物へ共有しない
- Bootstrapから必要な新規ペルソナを発見・追加できる
- 同じ状態から複数主体が独立経験を持ち始める場合は別`PER-xxx`へforkする
- 再初期化は過去stateを上書きせず、同じ同期点から再構成する
- 一つのBootstrapは原則として一つのtarget story timeを持つ

最初の現代開始同期点として `BOOT-001 @ T0-MODERN @ none` を候補とし、PER-001〜004とworld stateを同期する。PER-005は1980年代側なのでBOOT-001ではstateを初期化しない。

### 理由
ペルソナ数が増え、人物状態と世界状態が時間とともに変化すると、別セッションや再生成時に個別ファイルだけから復元すると異なる時点・異なる世界versionの情報が混ざりやすい。

共通背景からworld/persona stateを情報境界つきで射影すれば、実体の独立性を保ったまま同じstory timeへ同期できる。また、小説でよく使われる「始まりの背景」を、読者向け説明だけでなく実際の世界・人物初期化へ利用できる。

`work/story-bootstrap` で人間レビューし、受理された場合に `ACTIVE` とする。
